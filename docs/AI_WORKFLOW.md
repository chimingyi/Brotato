# AI 辅助开发流程记录

这份文件记录这个游戏怎样从一句想法变成可玩的第一版，也说明哪些工作由 AI 完成、哪些判断仍然需要开发者自己做。

## 最初的想法

原始需求是：“我是一个初中生，想用 AI 做一个土豆兄弟类游戏，以前没做过游戏，希望记录 AI 开发游戏的整个流程。”

我们把大目标改写成了一个可以检查的第一版目标：

> 玩家可以在电脑或手机浏览器中完成一局 5 分钟的原创俯视角生存游戏。玩家能移动、自动攻击、收集经验、选择升级；失败或胜利后可以重新开始。

## 为什么选择浏览器技术

开始时电脑没有检测到 Godot 或 Node.js，但有 Python 和浏览器。因此第一版选择：

- HTML：放游戏画布、按钮和信息栏。
- CSS：控制界面外观和手机布局。
- JavaScript Canvas：每一帧更新与绘制游戏。
- Python 本地服务器：只负责把文件提供给浏览器，不参与游戏逻辑。

这样不用先安装大型引擎，双击文件或运行一条命令就能看到结果，也可以直接发布到 GitHub Pages。

## AI 实际做了什么

1. 检查空仓库和电脑环境，提出适合当前条件的技术路线。
2. 把游戏拆成移动、战斗、成长、内容、体验和发布六个阶段。
3. 每完成一个阶段就修改代码、启动网页并在真实浏览器中测试。
4. 把测试数字、发现的问题和修复方法写入开发日志。
5. 用简单图形生成原创角色与敌人，不复制其他游戏的素材。

## 人仍然需要做什么

AI 可以快速写出代码，但不能替玩家决定“好不好玩”。开发者需要：

- 亲自玩几局，感受移动速度、敌人数量和升级强弱。
- 说出自己喜欢或不喜欢的地方，不需要使用专业术语。
- 为原创世界观、角色名字和美术风格做最终选择。
- 检查 AI 生成内容是否符合自己的目标，不能只因为代码很多就认为已经完成。
- 管理自己的 GitHub 登录、账号安全和发布设置。

## 有效的提问方式

一次只说清楚一个可验证目标，效果通常最好。例如：

```text
请加入一种移动很快、生命较低的敌人。
它要在生存 15 秒后出现，颜色和普通敌人明显不同。
完成后请实际运行并把测试结果写进开发日志。
```

如果发现手感不好，可以直接描述感受：

```text
第三种敌人太难打，我经常还没升级就失败。
请先分析是生命、速度还是出现时间的问题，再只调整一个数值让我比较。
```

## 本次流程中 AI 也会犯错

- 第一版生命显示没有限制最低值，出现过负数。
- 手机界面第一次测试时按钮和经验条重叠。
- 长时间自动测试超过了工具时间限制，需要拆成短测试。

这些问题说明：AI 生成代码以后必须运行、观察和记录。开发流程的重点不是“一次生成完美代码”，而是“小步完成 → 实际测试 → 发现问题 → 修复 → 记录”。

## 后续迭代建议

第一版发布以后，再按玩家反馈选择下一项，不要同时扩展所有内容。适合的顺序是：

1. 调整数值，让前 1 分钟既不会太空，也不会突然失败。
2. 增加一名拥有不同初始能力的角色。
3. 增加武器选择界面和更多构筑组合。
4. 使用原创图片替换程序绘制的简单形状。
5. 加入更多音效、背景音乐和无障碍设置。
